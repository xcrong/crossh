# Design

## Context

现状见 `proposal.md` 的 Why。设计前需要固定的几项现状约束：

- `search` 只有一条出口（`crates/crossh-note/src/lib.rs:478`），视图层 `crates/crossh-note-view/src/window.rs:324` 只在查询非空时调用它，并按返回顺序渲染，输入已经过 `SEARCH_DEBOUNCE` 防抖。
- FTS5 表 `notes_fts` 的 tokenizer 对中文不切词，中文查询在 FTS 上必然零命中；这是既成事实，不是本次要修的索引问题。
- 排序目前完全落在 SQL 里（`pinned DESC, updated_at DESC, id DESC`），两条路径各自 `ORDER BY`，没有统一的排序点。
- `crossh-note` 是零 `gpui` 的纯逻辑 crate，可以本机跑完整测试；Windows / Linux 上行为一致（只有 SQLite 与字符串处理），因此没有需要交给 CI 验证的平台分支。
- 预算约束来自 `AGENTS.md`：最小 diff、不写兼容层、不引入新依赖。

## Goals / Non-Goals

**Goals:**

- 把「返回哪些笔记」和「按什么顺序」从两条 SQL 各自决定，收拢到一处可单测的排序逻辑。
- 让混合查询（中英混排）不再漏结果，并且两条路径的命中可以同尺度比较。
- 保持 schema、依赖、对外签名不变，使这次变更可以只靠 `cargo test -p crossh-note` 验证。

**Non-Goals:**

- 不做中文索引（trigram tokenizer、影子 bigram 列、FTS5 自定义 tokenizer）：都能用，但都是 schema + 重建索引 + 写放大，而当前笔记库规模不需要。
- 不改视图层：命中高亮、片段预览、结果计数、跳转到命中位置都不在本次范围。
- 不引入 `bm25` 排序，也不做多路分数融合（RRF / 加权）：在只有 1~2 路、且其中一路没有分值的场景下，融合权重无法解释也无法测。
- 不清理历史 FTS 表里的 `unicode61` 选择问题本身；tokenizer 改动属于索引变更，留给「CJK 索引」这个独立变更。

## Decisions

### D1. 候选集合改为「并集 + 去重」，而不是换索引

`search` 变成：`search_fts` 取候选 id → `search_like` 取候选 id → 按 id 去重 → 统一排序。

- 替代方案 A：把 `notes_fts` 换成 trigram tokenizer。它能让中文走索引，但 trigram 对少于 3 个字符的查询无效，而两个汉字查询是最常见的输入，仍然要保留子串路径——等于同时维护两套索引和两套语义。
- 替代方案 B：影子 bigram 列 + trigger 维护。能真正加速 CJK，但 `SCHEMA_VERSION` 要 +1 并重建索引、每次写入要额外计算 bigram、还要处理 1 MiB 正文的写放大；当前没有任何性能数据支持这笔开销。
- 选择并集：修的是「漏结果」这个确定性缺陷，成本是每次查询多一次 FTS 调用（本来就跑），不触碰数据模型。

### D2. 排序用「能从正文算出来的证据」，不用 bm25

排序键固定为 `(pinned, 命中次数, 首次命中位置, updated_at, id)`，全部由笔记自身推导，实现为 `crossh-note` 内的纯函数（入参是内容与查询词，出参是证据），因此可以完全不碰 SQLite 单测。

- 替代方案：FTS 侧取 `bm25(notes_fts)`，子串侧用命中次数当分数，再混排。问题在于两种量纲不可比，混排权重只能凭感觉；而且 `bm25` 只在 FTS 命中的行上存在，中文笔记会永久落在「无分值」区间。
- 代价：与直觉上的相关性（稀有词权重、词频归一化）有差距。可接受——笔记检索的候选集通常只有几十条，用户真正需要的是「不漏 + 顺序稳定」，而不是严格相关性。

### D3. 子串路径按空白切词做 `OR`，并把 `%` / `_` 转义

`search_like` 接收词列表，拼接为 `content LIKE ? ESCAPE '\' OR content LIKE ? ...`，每个词独立转义。整串 `LIKE`（现状）会让 `hello 天气` 这种多词查询在子串路径上必然零命中，与规格里的并集语义冲突。

空词在切词阶段就被过滤；查询只含空白时直接走 `list()`（不构造 `LIKE '%%'`）。

### D4. FTS 容错：转义 + 失败降级，不向上抛错

`search_fts` 返回 `Result`，`search` 里把 `Err` 转成「只用子串路径」并 `log::warn!`。这样视图层只在**两条路径都失败**时才显示「查询失败」（现实中只剩数据库错误）。

替代方案：让 FTS 语法错误冒泡到视图，显示「查询失败」——用户输入一个未配对引号就看到错误页，体验不合理。

### D5. 已知上限与升级路径写进代码

子串路径是 `O(笔记数 × 正文长度)` 的扫描，且每次按键（经防抖）都会跑一次。这一点用 `ponytail:` 注释写在实现处：说明上限、说明升级到影子 bigram 索引的入口。规格里也保留同一条要求，避免「注释被删了就没人知道」。

需要如实记录的是：**纯 ASCII 查询的代价确实变大了**。旧实现在 FTS 命中时提前返回，不会再扫正文；并集语义要求每次都跑子串路径，否则 `wor` 命中 `world` 这类子串匹配和中文混排查询仍然会漏。这一取舍不在「今天本来就这么慢」的范围内，属于本次变更主动接受的成本。

## Risks / Trade-offs

- **每次查询都跑两条路径，纯 ASCII 查询也因此从 O(索引查询) 变成 O(索引查询 + 全表扫描)** → 输入已防抖，笔记库是个人规模；若实测有卡顿，先量化（笔记数 × 平均正文长度），再走 D5 的影子 bigram 索引，而不是加缓存掩盖。
- **排序与旧版不同**（相关度插到 `updated_at` 之前）→ 备注视图列表测试里若有依赖旧顺序的断言需要同步更新；这条变化写进 release notes 更合适，避免用户以为排序坏了。
- **多词 `LIKE` 拼接引入注入/转义风险** → 每个词单独 `%`/`_` 转义并走 `ESCAPE '\'`，配一条含 `%` 与 `_` 的用例（现有 `spec_20260827_note__search_like_escape` 扩展为多词）。
- **大小写不敏感只在 ASCII 范围成立**（SQLite `LIKE` 与 unicode61 都是如此）→ 规格明确写 `ASCII 大小写不敏感`，不对全 Unicode 做承诺。
- **`spec_20260903_note__fts_hit_preferred` 语义反转**（旧断言要求 `search == search_fts`）→ 按新语义改成「并集结果包含 FTS 命中、且顺序由统一排序决定」，并在 tasks 里单列。

## Migration Plan

无 schema 变更、无配置变更、无索引重建。上线即生效；回滚只需 revert 本次提交，笔记库保持可用（本次不动 `SCHEMA_VERSION`，也不改 `notes_fts` 定义）。规格在归档时由 `openspec archive` 合并进 `openspec/specs/note-search/spec.md`。

## Open Questions

- 是否要给结果加条数上限（例如 200 条）：现在返回全集，视图也未分页。等笔记库规模或视图性能提出要求时再定，加上限不改变本次规格的排序与集合语义。
